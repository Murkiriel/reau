# Changelog

All notable changes to REau are listed here, newest first, in the
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/) format. The app follows semantic versioning in its `0.y.z` form
(no 1.0 yet, so anything may still change between minor versions): release builds are called `0.3.0`, and debug builds add
the build date and time after `-dev+` (`0.3.0-dev+YY.MM.DD-HH.MM`, for example `0.3.0-dev+26.11.03-09.37`). Versions are listed
newest first; the days before 0.1.0 are kept below it as the project's history, each gathering what changed that day (days
with no change visible to people who use the app are not listed).

## [0.3.0]

> Not released yet: the owner decides the date. **If you used the Lite edition**, read the first entry of "Changed": this version is a new app for you.

### Added
- **A bench panel: a stand-in for the dash that runs on a computer** (13/11/2026; a tool only, in `scripts/painel_falso/`: nothing in the app changed; **not yet tried against a real phone**): `painel_falso.py`, in Python with the standard library alone, listens on the dash's UDP ports, answers the greeting with an RSA-1024 key pair made at each run (the private key is never written), takes the AES-256 session key, sends the dash's heartbeat, answers each video frame with the dash's notice, checks every RTP packet against the rules of the stream (sequence, source, the 90 kHz timestamp, the marker, the FU-A pieces), writes the video as a `.h264` file with the frames a second, the losses and the frames' sizes, presses the joystick from the standard input, and recognises the app's exit sequence. Everything goes to the terminal and to a log file, with the protocol errors counted. It is written from the app's own code and answers only what that code shows the dash answering: it proves the phone's side, not that a dash takes it. `--selftest` runs it against a minimal phone side on the loopback, with no network; a test reads the ports, the button codes, the packets and the exit sequence from the Kotlin sources, so the two cannot drift apart unseen; the CI runs its tests and the mutation test has twenty-three mutations of it. CONTRIBUTING says how to make the computer the access point the app looks for. `ponto_de_acesso.py` (14/11/2026) makes that access point on Linux with NetworkManager without taking the computer off its own Wi-Fi: a second, virtual interface on the same card, on the channel the computer's network is on (5 GHz included), with `check`, `up`, `down` and `--dry-run`; it refuses a card that cannot be a station and an access point at once, a channel where nothing may start transmitting and a network already in `192.168.1.x`, and its `up` **has not yet been run on a real card**, only its reads and `--dry-run`. `--ver` on the panel also shows the video live in an `ffplay` window while it is written, and a missing `ffplay` or a closed window costs only the view.
- **A release build over an old build gives the same APK as a clean build** (13/11/2026; build only, nothing in the app changed): the Kotlin compilation of the release (and of the `benchmark` build) is no longer incremental when a source changes, since an incremental one made the Compose compiler write other constants and `classes2.dex` and `classes3.dex` differed from those of a clean build of the same commit. The debug build stays incremental. A release after a change now compiles all the Kotlin again (about a minute more).
- **Dependency check by PGP signature** (13/11/2026; build only, nothing in the APK): `gradle/verification-metadata.xml` now has `verify-signatures` on, with the trusted keys exported to `gradle/verification-keyring.keys`. An artifact is checked by the signature of its publisher when it has one and by the sha256 it already had when it has not (many artifacts of Google's Maven are not signed); no sha256 entry was removed. CONTRIBUTING says what to do when a new dependency asks for a key.
- **Coverage of the unit tests with Kover, a macrobenchmark module and a device that Gradle manages** (13/11/2026; build and tools only: no code, permission or component in the release APK changed): (1) `./gradlew :app:koverHtmlReportDebug` writes the coverage report of the JVM unit tests (Kover 0.9.11). (2) The `macrobenchmark` module has `StartupBenchmark` (cold start with and without the baseline profile) and `BaselineProfileGenerator` (what runs while the app opens), on `androidx.benchmark:benchmark-macro-junit4` 1.5.0; they run on a device and are not part of any test run. They measure a new `benchmark` build type of the app (the release code, signed with the debug key), which is not a build for the rider. The hand-written baseline profile stays. (3) A Pixel 6 with API 34 is declared as a device that Gradle manages, for the instrumented tests and for the benchmark; declaring it downloads nothing. CONTRIBUTING has the commands.
- **"Check for updates" shows the signature of the installed APK, next to the project's** (13/11/2026; Settings, last group; nothing is asked of the network for it): the fingerprint (SHA-256) of the certificate that signed the installed APK, read from Android's own record of the package, in a monospace font that can be selected and copied, next to the fingerprint of the project's release key (`SigningCheck.EXPECTED_SHA256`, `63f5c3ba687699b0b4288a878bd8372bed2c9632222d7f673ea71073aa208970`, the certificate of the Releases 0.1.0 and 0.2.0, confirmed by the owner), and whether the two match. On a debug build, which is signed with the debug key, a signature that is not the project's is told neutrally ("Debug build: it is signed with the debug key, not with the key of the project's releases"); on a release a difference is shown as a difference. Three languages.
- **The GitHub workflow attests the APK it builds** (13/11/2026; `.github/workflows/ci.yml`, job `auditoria-apk`; the workflow still publishes nothing): after the release APK is built and audited, on a push to `main` only, the `actions/attest-build-provenance` action (v4.2.2, pinned by commit like the others) records, signed by GitHub, which commit and workflow produced that file. Only that job asks for `id-token: write` and `attestations: write`. It covers the APK the workflow builds (signed with the debug key and not kept) and promises nothing about the Releases, which are signed on the maintainer's computer with the project's key; the site does not mention it.
- **The install page checks the APK by the fingerprint of its signature** (13/11/2026; the three languages): a new section "Checking the APK" gives the whole fingerprint of the project's key (`63f5c3ba687699b0b4288a878bd8372bed2c9632222d7f673ea71073aa208970`), says where the app shows it (Check for updates) and how to read the one of a downloaded file on a computer (`apksigner verify --print-certs`).
- **A first-time fit assistant, on the Android Auto screen** (13/11/2026; **no proof on another phone yet**; nothing changes for whoever already has a fit saved): the factory fit (the place of the navigation crop, for one) was adjusted by eye on a single phone, and on another one Android Auto may draw the maneuver arrow or the speed outside the part that reaches the dash's glass. On a phone that never saved a fit, the "Fit to the dome" section opens with a card of four steps: (1) open Waze or Maps in Android Auto and start a route (Start turns the Mask on, if it is off); (2) do the maneuver arrow and the distance show whole in the clear part of the picture? (3) does the speed show whole? (4) done. Each "No, adjust" shows only the controls of that step, which are the Navigation tab's own (the place of the crop for the maneuver; its size and its vertical place for the speed; "Move" when the mode is Whole image), and each tap applies at once and is already saved, as on the tab. The assistant picks no value by itself and has no fit of its own. It can be skipped; finished or skipped, it does not open by itself again, and the quiet "Fit assistant" button, under "Reset to default", opens it again. It says when Android Auto is not showing the navigation and when the DPI asked is not the 180 the factory fit was measured at. Every button is 48 dp or more. **Defaults by DPI:** what Android Auto draws does not depend on the phone's screen: REau always asks for 800×480, with the DPI and the margins of the settings. So the key of the defaults is the DPI asked, and the new table (`FitDefaults`) has one row only, the measured one: 180, with the values of today. No other DPI got a row, because nobody measured one: they all keep getting the fit of today.
- **A "your own network only" notice next to the network server's switch** (12/11/2026; a text only: the server did not change at all): on the Android Auto on the network screen, right under "Turn on the network server", and in sight whether the switch is off, on or still waiting for you to tap Turn on, the app says to use it only on a network of your own (your home, your phone's own hotspot) and never on public or someone else's Wi-Fi: the server is plain HTTP with no encryption, so anyone on the network can see the PIN, the picture and the touches. The warning that already showed with the server on (whoever has the address and the PIN sees the screen) stays where it was.

(2) **The alert channel muted or blocked in Android**: if "Dash alerts" has no sound and no vibration, an importance too low to make either, or is blocked (or all of REau's notifications), a card on the main screen says so, with a button to Android's page of that channel, and the ride log writes the same at the start of the projection and when it changes. (3) **The hung dash also in the earphone**: besides the notification, three short beeps (880 Hz, 780 ms in all, moderate volume) play once through the phone's output, the headset or the helmet's intercom, with the player that already carries Android Auto's sound. It is not shown on the dash because a hung dash is one REau cannot talk to (it refuses every join, there is no link to send a card on). **No proof on the bike yet.**
- **A notice where the recordings are switched on and where they are shared** (11/11/2026; nothing about what is recorded changed): Settings > Debug says in plain sight, above the two recording switches and under the Share buttons, that the recordings contain the map (where you rode) and the names of who calls.
- **The exported zip is masked** (11/11/2026; Settings > Debug > Share): the logs inside it go through the same masking as the collection script's copy for sharing: the dash's Wi-Fi name, every MAC address and the names of the other Wi-Fi networks (the name that follows `SSID`, `ssid=` or `configKey=`, hidden in every log of the zip), and the name of the paired dash. The recordings are binary and go as they are.
- **Seven more experimental switches, all off by default** (11/11/2026; with each one off the app does exactly what it did before; **no proof on the bike yet**; each one is written in the ride log with the settings in use and on the line `connection experiments ON: …`, and the start guard knows it). (1) **"Old weather leaves the dash"** (Settings > "Experimental dash"; counts at once): the weather in the dash's heartbeat goes away 30 minutes after it was fetched, not 3 hours. The heartbeat has room for a temperature and an icon and none for an age, so the safer choice for the rider is to send nothing rather than an old reading as if it were current. (2) **"Frame ceiling by battery heat"** (Experimental video; at once): this phone's thermal status never leaves `thermal=none`, so the battery temperature the app already reads every 5 s also lowers the frame ceiling: to 3/4 from 44 °C, 5/8 from 46 °C and 1/2 from 48 °C, each step left 3 °C lower; the log says each change (`[heat]`). (3) **"GPS speed for the profiles"** (Experimental video; at once): the near/far speed profile reads the speed of the GPS fix when a route runs, "Use location" is on and the GPS is *already* listened to for the dash's info ring; otherwise the route's estimate, as always (it erred 11 km/h on average). REau does not switch the GPS on for this: that would be a continuous GPS. (4) **"Recalculating on a short inactive"** (Experimental dash; at once): the real recalculations reach the dash as Android Auto's navigation status "inactive" for 1 to 7 s, and the route card cleared at each. Now such an "inactive" shows the recalculating compass (or the lost-signal icon) with the last distances for up to 8 s; a route that really ended (an arrival, the end of a session) still clears at once. (5) **"Explicit encoder colours"** (Experimental video; from the next video): the dash's encoder is asked for BT.601, limited range, SDR (`KEY_COLOR_STANDARD`, `KEY_COLOR_RANGE`, `KEY_COLOR_TRANSFER`); a codec that refuses is asked again as before, and the log says what it accepted (`encoder colour: …`). (6) **"Android Auto protocol 6.0"** (Experimental connection; from the next start): the handshake asks for version 6.0 instead of 1.7. If the handshake does not complete after asking it, every later one of the process asks 1.7 again (a second request on the same connection would leave Android Auto answering nobody), and the log says what was asked and answered. (7) **"More tolerant dash watch"** (Experimental connection; from the next start): the dash's silence only goes to the log at 12 s and ends the session at 60 s (4 s today), a keyframe is asked when it speaks again, and the control packets leave 12 ms apart (the button answers too, so a burst of them is slower by 12 ms per packet).
- **When the cable is plugged or unplugged, the projection comes back faster, and the log says why** (11/11/2026; no new switch; **no proof on the bike yet**): Android Auto closes the session of its head unit server at every change of the phone's USB (a cable with data plugged or unplugged; a mains charger does not do it), and the app used to wait a second before dialling it again. Now, when the session ends within a second of a USB change, the log says `the Android Auto session ended N ms after the USB changed (Android Auto closes its sessions on every USB change)` and the first new dial is made at once; after it the pace is the usual one, and any other end of a session is treated as before.
- **The exported report starts with a header** (11/11/2026; Settings > Debug > Share): the first file of the zip, `report-header.txt`, names the app and carries the line of the connection experiments that are on at that moment (`connection experiments ON: …`, or that none is), so the person who opens the zip reads it before any log. The logs are as they were.
- **One more experimental switch, off by default: "Day and night with memory"** (10/11/2026; Settings > "Experimental video"; **no proof on the bike yet**): with the map theme by the sun, the projection asked whether it was night with a new clock at every look, so the band between day and night always counted as day: dusk came out right and dawn came about half an hour before sunrise. With the switch on the band keeps the answer of the look before, as the theme's rule always said; off, nothing changes.
- **Four more experimental switches, all off by default** (10/11/2026; with each one off the app does exactly what it did before; **no proof on the bike yet**; each one is written in the ride log with the settings in use and on the line `connection experiments ON: …`). In Settings > "Experimental video" (a new group): (1) *Rebuild a silent encoder*: if the video encoder takes frames in and gives none out for 3 s, with no error, it is rebuilt as a failing one already was, up to 3 times per stream (before, only an encoder that threw an error was rebuilt, and a silent one left the dash frozen with the app saying it was streaming); the ride log says `encoder mute (experiment): …`. (2) *Longer pause when asking for a keyframe*: when Android Auto's picture breaks and REau asks for a keyframe by taking the video focus away and giving it back, the focus comes back after 400 ms instead of 100 ms. With the switch on or off, the ride log now says how long the keyframe took after the request (`focus cycle: the keyframe came N ms after the cycle`) or that none came in 5 s, to compare the two values. In Settings > "Experimental connection": (3) *Ask for the dash on 2.4 GHz only*: the request for the dash's Wi-Fi names the 2.4 GHz band (Android 12 or later); as Android's documentation warns that a phone may not accept a request by band, a request with the band that goes unanswered is followed by one without it. (4) *Guard the start*: if the app's process ends within 10 s of a start made with some experimental switch on, the next opening switches the experimental switches off (the guard stays on) and says so in the ride log.
- **Log: the version Android Auto refused** (10/11/2026): when Android Auto answers the version request with a status other than 0, the log says the version was not accepted; the handshake goes on as before. **Collection by adb:** `INFO.txt` now carries three Android settings that make the system refuse a socket on a network (`restricted_networking_mode`, `always_on_vpn_app`, `always_on_vpn_lockdown`), read only.
- **Tests** (10/11/2026; nothing changes in the app): four new fuzz targets for what comes from Android Auto (the stream of messages, the video units, the video's size header and the navigation messages); the tests' fake dash checks every video packet against the rules of RTP and writes what it received as an `.h264` file; and each arrow byte the app sends to the dash has written down whether its drawing was ever seen on REau's own dash or is known only from the scan (the debug card has all of them, the roundabouts' other exit numbers aside).
- **Four experimental connection switches, all off by default** (10/11/2026; Settings > "Experimental connection"; with all of them off the app does exactly what it did before; each one is written in the ride log with the settings in use, and one more line `connection experiments ON: …` says which are on). They are ways of putting less load on the dash's small Wi-Fi access point, to be tried one at a time on the bike; **no proof on the bike yet**. (1) *Space out the video*: the RTP packets of a frame leave with a 2 ms pause after every 4 and no more than 400 packets in a second (the thread waits for the second to end), on the thread that already sends them (the encoder's output thread; no queue and no new thread); a keyframe no longer goes out as a burst of a dozen packets. (2) *Mark Wi-Fi priority on debug builds*: a debug build marks the control and video sockets for Wi-Fi priority (the same values a release always uses: 192 and 136) instead of leaving them unmarked, which was the test of 28/10/2026; a release is unchanged. (3) *Lower, adaptive bitrate*: the normal stream aims at 200 kbps instead of 400 and, every 3 s, compares what the encoder really put out with the target: above 125 % it asks for `current x target / real` (never under 64 kbps), under 70 % with the request below the target it raises it 15 %; it is a live parameter of the running encoder, which is never rebuilt, and the keyframe stays at every second. Dropping to 2 fps and 100 kbps when the dash leaves the navigation screen is **not** done: the dash's `09 04 55` notice is, in REau's own logs and notes, a rare "frame decoded" notice (3 in 756 rides), not a sign of a screen change. (4) *Wi-Fi and EPERM*: the projection's Wi-Fi lock is asked as the low-latency one on Android 10 and later. **On Android 14 or later this part changes nothing**: by Android's documentation, the "high performance" lock the app always asked for is already swapped by the system for the low-latency one from Android 14, and the low-latency one acts only with the screen on and the app in front (the ride log says so on the line of the locks). The other part counts on every Android: when Android refuses to bind a socket to the dash's network (EPERM), the same network is tried again up to 5 times, 400 ms apart, before it is let go and asked for again as before.
- **The ride log says how long the start-up takes when it is slow** (10/11/2026; diagnostics only: nothing about the first frame, the screens or the projection changed): one line `[startup] Application.onCreate took 83 ms` (and the same for `MainActivity.onResume` and `ProjectionService.onStartCommand`) when one of them takes **more than 50 ms**; at 50 ms or less nothing is written. It tells which of the three is behind the 1.3 s of the first frame (A-13). Also, the rotation of old ride logs and the trimming of the diagnostic folder (which sort every file in `diag/`, so they grow with its size) no longer run inside `Application.onCreate`: they run on a thread of their own right after the new log file is created, which they never remove.
- **Maneuver distances in miles and feet when the dash is set to miles** (08/11/2026; the branch of the dash panel, item 1 of the survey of the maker's app; **no proof on the bike yet**): the distance to the maneuver and the total (`05 04`, `05 09`, units in `05 06` and `05 46`) go in tenths of a mile (`0x20`) above 550 feet and in feet (`0x50`) below, 3.281 feet to the metre; metric is unchanged. The dash's own unit (`03 04`) decides, the phone's region only before the dash has said it, and the ride log says which one is in use. There is no new switch.
- **The real volume in the heartbeat** (08/11/2026; **no proof on the bike yet**): `05 4C` (music) and `05 1B` (call) go as `0x10` plus a level from 0 to 10 (the music and the voice-call stream of Android, in eleven steps), read in the same once-a-second turn that builds the heartbeat; before they were the fixed values of the capture. Behind "Phone status", as the rest of the heartbeat's phone fields.
- **The heading of the last GPS fix in `05 2D`** (08/11/2026; **no proof on the bike yet**): two bytes, 0 to 359 degrees, only with the phone at 1 m/s or more, a fix of at most 10 s and "Use location" on; otherwise zero, as before. REau does not turn the GPS on for this: it uses the one the info ring's GPS card already listens to (off by default).
- **A discreet line on the main screen when the old Lite app is still installed** (03/11/2026): "The old REau app (the one with the seal on its icon) is still installed. It isn’t needed any more: you can uninstall it." The warning that Android Auto does not answer names it as well, since both dial the one head unit server, which takes a single session at a time.
- **The ride log says more about the codecs and about where the video path spends its time** (03/11/2026; diagnostics only: nothing about the video, the codecs or the pace changed). (1) A failed codec is told with its error code, whether it recovers, whether it is transient and the driver's own diagnostic (`CodecException: … [codec=c2.qti.avc.encoder errorCode=1100(insufficient resource) recoverable=false transient=true diagnostic=…]`), in the decoder, in the encoder's start and in its output thread. (2) Once per session, a `codecs:` line for the decoder and one for the encoder: the H.264 codecs the phone lists (hardware or software, whether each takes the size and Baseline) and the one in use; and, for the encoder, `encoder accepted:` and `encoder output format:` with what the codec took of what was asked (`latency`, `bitrate-mode`, `profile`, `i-frame-interval`, …) and what it did not (`differs: latency asked 1 got -`). (3) `codec metrics (decoder|encoder …)`: the framework's own `MediaCodec.getMetrics()` (mime, size, error code, latency of each buffer, …) once when each codec is let go, read on a thread with a 300 ms limit so a hung driver cannot hold the end of the session. (4) The `video fps` line gets new fields at its end (the original ones keep their place and format): `compose_max`/`compose_p95` and `encode_max`/`encode_p95` (the worst frame and the 95th percentile of the window, not only the mean), `look=n/mean/max` (what the picture look costs, counted apart from the compose), `latch=n/mean/max` (the `updateTexImage` of each new picture) and `wake=N(rate/s)` (the pictures from Android Auto that woke the compositor, against the `drawn=` of the line). Nothing allocates per frame. `ler_registro.py` shows them in the `video:` summary (worst frames, look and latch cost, wakeups per second against pictures drawn per second). To read on the next ride; the session with Perfetto/simpleperf on the phone stays for later.
- **A notice, with sound and vibration, when the phone gets hot** (03/11/2026): the Android thermal status follows the skin and stayed at `none` while the battery held 40 to 42 °C for 90 minutes with the charger in (ride of 01/11/2026); in the summer sun, a closed pocket or a tank bag the battery adds 8 to 10 °C and passes the 45 °C where Android cuts the charge and slows the phone. When the battery reaches 44 °C during a projection, a notification in the "Dash alerts" channel (high importance, sound and vibration, the same channel as the stuck-dash notice) says the phone is hot and suggests taking it out of the sun or the closed pocket, or unplugging the charger; once per projection, and a new one only after the battery falls under 41 °C and passes 44 °C again (the notice goes when it cools, and when the projection ends). The ride log gets a `[heat]` line each time, and `ler_registro.py` shows it in the timeline. In English, Portuguese and Spanish.
- **The rider's mark keeps a copy of the Android Auto session recording** (when the session recording option is on; 03/11/2026): the recording is a ring of 100 MB (768 MB in a debug build) that overwrites itself (about 11 minutes of a long ride survive in a release), and the mark of 19:15:51 on 01/11/2026 was gone by the time the phone was read. Now the mark copies the two halves of the ring, as they are at that moment, to `reau_<date>_<time>_marca.1.aasession` and `reau_<date>_<time>_marca.aasession` in the same `sessions/` folder, a name the ring never writes to. The copy runs on a thread of its own (the Android Auto read thread is not held), only if there is room (the copy plus 100 MB free), and keeps at most 3 copies or 250 MB (the oldest go, never the one just made). Marks in the same stretch of the ring share one copy, which the later mark replaces by a larger one. The ride log says `mark N: the session recording is kept as …`; `coletar_do_celular.sh` already copies the whole folder and `scripts/dev/teste_cego/extrair.py` takes the pair like any other.
- **A notice, with sound and vibration, when the dash's Wi-Fi hangs** (02/11/2026): in the ride log of 01/11/2026 the dash went quiet in the middle of the ride and, for 3 min 54 s, stayed in the Wi-Fi scan at a good signal (-47 to -63 dBm, the same channel) while 23 requests in a row ended unavailable in 6 s each; the rest of the dash worked, only the picture was gone, and it came back when the ignition was switched off and on. REau cannot undo that, but it now says so: once the dash had spoken in this projection, its Wi-Fi was lost, and at least 3 requests in a row (and 30 s) ended with the dash still in the scan at -75 dBm or better, a high-priority notice (a channel of its own, "Dash alerts") tells you to switch the ignition off and on, and the ride log gets `dash visible but refusing for 35 s (3 tries) — dash Wi-Fi likely hung; rider told to cycle ignition`. A dash that is switched off leaves the scan, so it never raises the notice; it is once per absence and goes away when the dash is back. The decision is `DashStuck` / `StuckDashWatch`, in the JVM tests.
- **The ride log says what REau was sending in the seconds before the dash went quiet** (02/11/2026): when the Wi-Fi is lost or a watchdog fires, one more line (`send tail before …`) gives how long the link had been up, the RTP packets and bytes of each of the last 10 seconds before the last packet, the biggest burst of packets back to back, the last keyframe (bytes, packets, how long before) and the last command that is not a heartbeat. It is kept in arrays that exist already (no allocation per packet), and the lines that were there are unchanged. To find what sets the dash's Wi-Fi off.
- **`ler_registro.py` knows the new cases** (02/11/2026): the same `EPERM` on the same `network=` twice or more is a defect (the dead network handed back); a dash whose Wi-Fi returns within 5 minutes (it was 2) is its Wi-Fi restarting, not the bike switched off; the new "dash visible but refusing" line (and, in older logs, two or more requests that ended with the dash in the scan at -75 dBm or better after 30 s) is a hung dash; and "transmitting with no confirmation of the first frame" is no longer said of a projection that lasted under 10 s.
- **The debug build keeps 1024 MB of recordings and 1024 MB of logs, each on its own** (03/11/2026; owner's decision; the release build is unchanged: 200 MB and 200 MB). The recordings are the video sent to the dash, the session recordings and the copies a mark keeps, counted together (`RecordingsSpace`, the oldest going first); the logs and the diagnostic folder have their own budget (`DiagSpace`). What changes is the session recording's ring: it was 100 MB in every build, which on 01/11/2026 overwrote 1 h 30 of a long ride; in a debug build it is now 768 MB (three quarters of the budget, the rolling video takes the rest), and shrinks when the phone would be left with less than 512 MB free (never below 100 MB). The mark's copies may be up to the whole 1024 MB in a debug build (3 copies at most, as before); the free space they need (the copy plus 100 MB) is the same. The (i) of the two recordings says the numbers.

### Security
- **The web viewer's page no longer asks the browser to run any inline script or style by permission of the whole page** (both editions; 28/10/2026; item A-12 of the independent evaluation): the content policy sent with the page said `'unsafe-inline'`; now only the page's own script and style run, because they carry a nonce that is new in every answer (128 random bits, said in the header and written in the page's tags), and a script that got into the page cannot know it. The rest of the policy is as it was (the page's own address, the video, the socket; no frames around it, no plug-ins, no form posts). Opened in a real browser, the page works with the right nonce and shows nothing with a wrong one.
- **A key-exchange rejection after the key was confirmed is ignored** (both editions; 27/10/2026, independent review; packets are still taken from any address): before, a `07 01` “rejection” from anybody on the dash’s Wi-Fi (its password is the same on every dash) started the exchange over at any time, and the first key to answer got the new session key (and the caller’s name of the call card). The “first half of each kind” rule below only held inside one attempt.
- In a key exchange with the dash REau keeps the **first public-key half of each kind** in an attempt: the dash's Wi-Fi password is the same for every dash, so anybody joined to it could otherwise send a second copy of the key and replace the dash's. (Packets are still accepted from any address, so that a dash that answers from another one is not left out.)
- The **web viewer** only accepts a page that was opened from the phone's own address (a local number such as 192.168.x.x, or localhost), so a web page that tricks a browser into reaching the phone by a domain name (DNS rebinding) is refused even before the PIN; the **PIN no longer stays in the address bar or the browser history** (a reload asks for it on the page's keypad); a phone with several IPv6 addresses counts as one for the PIN's lock, which no longer grows without end, and a browser's close is answered.
- A **corrupt or cut packet from the dash** is now thrown away instead of being read as a shorter value, and a packet that makes REau's reading fail no longer takes the app down (twenty in a row end the session with a clear message).
- The **session key** of the dash's call card is only kept once it has really been encrypted for the dash, and the **first write of the app's protected settings** on two threads at once can no longer make two keys.
